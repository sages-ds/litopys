# Ворота якості пошуку

Будь-яка зміна ранжування власного API проходить лише через ці ворота. Перше питання — **«чи не стало гірше»**,
лише потім «чи стало краще». Вердикт: **GREEN / RED / NOT_CALIBRATED** — невиміряне не дорівнює зеленому.

Методи — лише з публічних джерел: nDCG@k (Järvelin & Kekäläinen, TOIS 2002), парний bootstrap різниці середніх
(Smucker, Allan & Carterette, CIKM 2007), LLM-суддя релевантності з калібруванням проти людини (Thomas et al.,
SIGIR 2024).

## Де що лежить

| Що | Де | Чому |
|---|---|---|
| Код: метрики, bootstrap, вердикт, суддя, сторінка оцінок | `evals/search/*.mjs` (тут) | без даних, можна в публічне репо |
| Збір видачі | `core/cmd/searcheval` (Go, не в образі) | той самий `core/query` Search, що й у продукті |
| Запити з класами, інциденти, оцінки власника, маніфест бази | приватне репо набору даних (далі `<dataset>`), тека `search/`; ранер клонує його в `bin/` | тексти запитів і особисті дані |
| Заморожена база | `litopys_searchbase_<дата>` на stage (`litopys-pg` :5433) — імпорт бази-джерела міграції (`-Source`) | реальний корпус живе там; базу `litopys` пілоту не чіпаємо |
| Сторінка оцінок | `bin/search-gate/grade.html` | містить тексти пам'яті — ніколи не комітиться |
| Звіти | `evals/search/results/*.json` | лише id і числа |

## Запуск

```powershell
pwsh -NoProfile -File evals/search/run.ps1 -Freeze     # раз: заморозити базу (потім маніфест → <dataset>/search/frozen.json)
pwsh -NoProfile -File evals/search/run.ps1 -Page       # базовий прогін (робоче дерево проти себе) + сторінка оцінок
pwsh -NoProfile -File evals/search/run.ps1 -BaseRef main -BaseEngine v2 -CandEngine v2 -Experiment search/experiments/<id>.json   # зміна ранжування v2 (база — main)
node --test evals/search/lib.test.mjs                  # юніт-тести (CI)
```

Код виходу: 0 GREEN, 1 RED, 2 NOT_CALIBRATED, 3 відмова (зміна ранжування без передреєстрації), 4 UNDERPOWERED.

## Правила вердикту

**З 2026-10-19 (рішення власника за дискусією трьох спеціалістів) вердикт виносить точний парний
randomization-тест, а не інтервал bootstrap.** На 3–4 запитах percentile bootstrap давав хибний RED у ~10–12 %
тестів і «GREEN через ширші інтервали» (x10). Правила нижче — чинні; bootstrap лишився описом.

1. **Інциденти — храповик.** `search/incidents.json`: запит → що має бути в топ-10 (`must_find` або
   `must_find_any`). `kind: guard` — мусить знаходитись завжди, хоч би що знаходила база; `miss` — відкрита ціль.
   **RED**, якщо кандидат губить інцидент, який знаходила база, або будь-який `guard`. Що знайшла злита версія,
   стає `guard` (поле `ratchet` каже, коли й чому). Новий промах у проді = новий інцидент до виправлення.
   Guard повертається в `miss` лише рішенням власника з причиною в `ratchet` (o-6, 2026-11-10, #276).
1a. **Щоденник воріт не міряється.** Записи пам'яті про самі ворота називають id запитів (o-6, golden-3, m-57) і
   цитують їх дослівно — на більшому корпусі вони витісняють справжні відповіді (#276: R-861, R-866 для o-6).
   `run.ps1 -Quoting` складає список записів, що називають id запиту воріт (`bin/search-gate/exclude.json`;
   текст запиту ознакою не є — запис із ним часто і є відповіддю). Список переглядають і комітять як
   `search/exclude.json` у litopys-golden. Коли він є, збір іде на k + |exclude| рядків, а `verdict.mjs --exclude`
   прибирає ці записи з обох боків до будь-якої метрики й обрізає до k. Після перезаморожування список складається наново.
2. **База — завжди `-BaseRef`** (зазвичай `main`). Старий рушій v1 видалено: експеримент без `-BaseRef` відмовляє, бо робоче дерево проти себе нічого не доводить.
3. **Класи запитів пам'яті** (тексти — лише українська й англійська; **ПІДТРИМКИ РОСІЙСЬКОЇ НЕМАЄ**): `identifier`,
   `natural_uk`, `natural_en`, `typo`, `decision` («що вирішили / чому / що не вийшло»). Клас вирішує лише з
   **≥ 6 запитами holdout** (`MIN_N`); менший — **лише опис**. Для класу, що вирішує, ΔnDCG@10 на holdout перевіряє
   точний sign-flip (Smucker, Allan & Carterette, CIKM 2007; повний перебір до 20 запитів), односторонній α = 0.025:
   - доведено гірше (Δ < 0) — **RED**;
   - доведено **не гірше за −δ, δ = 0.05** (non-inferiority, δ задав власник) — гаразд;
   - ні те, ні інше — **UNDERPOWERED**: доказів немає ні в той, ні в інший бік, і це не GREEN.
4. **junk@10** — частка оцінок 0 у топ-10 — **лише опис**: від фактичної довжини списку вона заохочує короткі
   видачі, а nDCG — довгі. Звіт несе метрики секцій (`sections`, описово; видача v2 позначає кожен рядок `match`):
   **hit@k** — у топ-k запиту з відповіддю є оцінка ≥ 2 (з парним sign-flip на «гірше» й «не гірше за −δ»);
   **junk_in_full** — частка нулів серед рядків, які видача подає як повний збіг (у v1 — усі, якщо список не `relaxed`);
   **false_confidence** — частка запитів без відповіді в пам'яті, де видача все одно каже «повний збіг».
5. **Запечатаний набір** (`<dataset>/search/sealed`): 100 реальних запитів із журналів Claude Code
   власника, пул v1 + v2 без мітки рушія, сліпі оцінки окремих агентів (`delegate:claude-blind`), класи й
   `answerable` від них. `run.ps1 -Sealed …` міряє на ньому (лише агрегати; `-Page` заборонено), кожен запуск
   пишеться в `sealed/usage.jsonl`. **Раз на реліз**; holdout із 2026-10-19 — набір для
   налагодження.
4. **NOT_CALIBRATED**, якщо в топ-10 holdout бази чи кандидата є результат без оцінки власника і без оцінки
   відкаліброваного судді.
5. **Train / holdout** — стратифіковано за класом, ~30 % holdout, розподіл записаний у `queries.json` і не
   змінюється (`assignSplits`). Підбір параметрів — лише на train. **N < 100** на клас — звіт `exploratory`:
   розвідка, не висновок.
6. **Передреєстрація.** Зміна ранжування оцінюється лише проти `search/experiments/<id>.json`, написаного до
   прогону: `id`, `hypothesis`, `prediction` (очікувана Δ за класами), `registered_at`. Негативні результати
   записуються так само, як позитивні.
7. **Однаковий субстрат.** База й кандидат — дві збірки `searcheval` на одній замороженій базі; база заморожена
   до першої зміни ранжування власного API. Заморожено **дані** (журнал). Схему й проєкції `run.ps1` перед збором
   доводить до коду: `migrate up`, а за застарілої версії проєктора — `projector rebuild` з того самого журналу.
8. **Збій збору — відмова.** Якщо пошук хоч одного запиту впав або результату немає з будь-якого боку, вердикт —
   відмова (код 3), а не GREEN над двома порожніми списками. До 2026-10-18 цієї перевірки не було: на базі без
   міграції 0023 кожен запит падав, а ворота давали GREEN.

## Оцінки й суддя

- Шкала: 3 — саме те, що шукали; 2 — релевантне; 1 — дотичне, не допомагає; 0 — не те / сміття.
- Оцінки — JSONL `{query_id, statement_id, grade, grader, at}` у `search/grades/`. Власник: `grader = "owner"`
  (сторінка `grade.html` → «Завантажити»). Оцінка власника завжди переважає.
- **Суддя** (`judge.mjs`) — рішення власника 2026-10-07: локальна модель (Ollama), лише після переїзду
  (сигнал власника). Закріплений: `judge:<model>@<digest>#<хеш промпту>`; новий digest чи промпт = новий суддя.
  Його оцінки враховуються, лише коли `calibrate()` проти оцінок власника дає ≥ 90 % збігу в межах ±1 на ≥ 100
  парах. До того — **NOT_CALIBRATED**.

## Експерименти (2026-10-07)

Аналіз базової видачі: 105 з 247 оцінок — 0. Сміття зосереджене в OR-фолбеку (`relaxed`, 18 з 29 оцінених запитів):
там 49 % нулів у топ-10 проти 25 % у строгому пошуку. «Стан todo — <дата>» дає лише 5 нулів (один запит).

| Експеримент | Гіпотеза | Вердикт | Звіт |
|---|---|---|---|
| x1-relaxed-min-coverage | у фолбеку вимагати збіг ≥ ceil(n/2) слів запиту | **RED** (спростовано) | `results/2026-10-07-2027.json` |
| x2-relaxed-idf-coverage | фолбек сортувати за сумою IDF збіглих слів (BM25 IDF) | **GREEN**, але гіпотезу не підтверджено (2026-10-18, після делегованих оцінок) | `results/2026-10-18-1918.json` |
| x3-identifier-literal-tier | запит-ідентифікатор: записи з дослівним входженням — першими | **GREEN**: identifier ΔnDCG@10 +0.045 [+0.001, +0.098], junk без змін; у main | `results/2026-10-18-1927.json` |

**x1.** Кандидат ⊆ база, неоцінених немає, тож вердикт виміряний. ΔnDCG@10: natural_ru −0.56 [−0.88, −0.02], decision −0.14,
natural_en −0.11, natural_uk −0.10. junk@10 для uk/en не впав, бо частку рахують із меншої видачі. Причина: у
перехресномовних і довгих запитах релевантне збігається одним рідкісним словом, і фільтр відрізав саме його.
Урок: сигнал — рідкісність збіглого слова, а не кількість збігів.

**x2.** Код у гілці `search/x2-relaxed-idf-coverage`, у main не злито. Він приводить у топ-10 нові документи. Якщо всі
вони сміття, natural_uk (−0.12) і natural_en (−0.25) погіршаться. Остаточний вердикт — після оцінок власника на
`bin/search-gate/grade.html` (прогін з `-Page` на гілці x2).

**Виправлення воріт.** Неоцінений результат метрики рахують як 0. Раніше «гірше» за такими нулями давало RED з
пріоритетом над NOT_CALIBRATED, і x2 спершу отримав хибний RED. Тепер клас із неоціненими результатами — невиміряний:
вердикт NOT_CALIBRATED, а причина пояснює, що було б, якби неоцінені були сміттям. RED дають лише втрачені
інциденти й повністю оцінені класи.

Знахідки для першого експерименту: (1) junk@10 0.4–0.6 — під влучним результатом багато сміття, зокрема «Стан todo —
<дата>» з легасі-імпорту; (2) «фортиклієнт днс» не дав жодного результату — транслітерована кирилиця латинських назв не
матчиться; (3) golden-5 (довгий запит) повернув 1 результат замість 12 відкритих користувачем; (4) 3 miss-інциденти
(golden-3, 8, 11) — відкриті цілі.

- **Делеговані оцінки експериментів.** Власник дозволив Claude оцінювати і нові результати експериментів (`delegates.json`,

  GREEN над порожніми списками. Тепер збій збору — відмова (правило 8), а `run.ps1` доводить схему бази до коду (правило 7).
- **Клас identifier розширено** з 10 до 40 запитів (holdout 12): посилання `#N`, `obs N`, `mem-N`, хеші комітів, версії,
  IP і порти, шляхи, коди помилок, назви змінних і таблиць. Базова лінія identifier: holdout nDCG@10 0.847 / junk@10 0.318,
  train 0.826 / 0.551.

  (nDCG −0.13, junk +0.13). У main не беремо.

  події»), інші класи не зачіпає. Сміття він не прибирає (junk без змін). Наступні кроки: не добирати фрагментні
  збіги до ідентифікатора, коли дослівних вистачає; пошук за номером запису (`obs N` → сам запис) — на рівні фасаду.
