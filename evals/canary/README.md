# Канарка каналів

Відповідає на питання, **що з поверхні `/v1/mcp` доходить до моделі клієнта**: `instructions`, опис тула чи результат
тула. Discovery benchmark (`evals/discovery`) міряє поведінку. Канарка міряє доставку: чи модель узагалі бачила
текст.

## Маркери

Вмикаються змінними фасаду `LITOPYS_CANARY=<токен>` і `LITOPYS_CANARY_ACTORS=<id актора>,…`. Без списку акторів
фасад не стартує: канарка ніколи не доходить до всіх. Решта людей бачить звичайну поверхню. Код — `core/api/canary.go`,
тест — `TestCanary`.

| Маркер | Де | Що перевіряє |
|---|---|---|
| `CANARY-INSTR-HEAD-<t>` | перший рядок `instructions` | чи `instructions` доходять узагалі |
| `CANARY-INSTR-CORE-<t>` | одразу після `InstructionsCore` (~512 символів) | межа, яку клієнти OpenAI важать найбільше |
| `CANARY-INSTR-TAIL-<t>` | останній рядок `instructions` | обрізання (Claude Code ріже на 2 КБ) |
| `CANARY-DESC-<t>` | кінець опису `system_whoami` | опис тула |
| `CANARY-RES-<t>` | поле `canary` результату `system_whoami` | результат тула |

## Прогін

```
pwsh -NoProfile -File evals/canary/run.ps1 [-Clients claude,codex] [-Model <m>]
```

Тимчасова база на dev-PG, одна людина «Canary» з токеном профілю `core` і вендором клієнта, фасад на
`127.0.0.1:8796`. Токен канарки випадковий на кожен прогін, тож модель не може його знати чи вгадати. Запит: «виклич
`system_whoami` і повтори дослівно кожен рядок CANARY-, який бачиш, і де саме». Маркер зараховано, якщо відповідь
містить його точно. Ізоляція клієнтів та сама, що в discovery: лише цей MCP-сервер, без пам'яті, оболонки й
користувацьких налаштувань. Результати — `results/<дата>-<клієнт>.json`; відповідь зберігається з маркером, заміненим на `<t>`.

**Розбіжність із discovery 2026-10-07.** Тоді Codex 0.160.0 у сценаріях S2/S3 без підказки в `AGENTS.md`
не скористався Litopys, і висновок був «не отримує instructions і описів тулів». Канарка на тій самій версії показує,
що обидва канали до моделі доходять. Отже, найімовірніше, проблема в поведінці (модель не вважає Litopys пам'яттю
без клієнтської підказки), а не в доставці. **[припущення]** Це варто перевірити повтором discovery для Codex після
відновлення ліміту (2026-11-02).

**claude.ai, 2026-10-31.** Канали тула (опис, результат) доходять; `instructions` сервера — ні: модель прямо
каже, що інструкцій сервера в її контексті немає. Ще одна особливість: тули конектора відкладені — модель бачить
лише назви і довантажує схему й опис конкретного тула через ToolSearch. Наслідок для дизайну: усе, що модель на
claude.ai мусить знати до першого виклику, має бути в описах тулів, з якими вона стартує (`project_resume`,
`system_guide`), або в їхніх результатах, а не в `instructions`. Профіль конектора — `core` (scope `litopys:core`).

## Ручна перевірка на хмарних клієнтах

1. Отримати id свого актора: `system_whoami` → `actor.actor_id`.
2. Увімкнути канарку на stage лише для цього актора: шаблон компоуза має порожні `LITOPYS_CANARY` /
   `LITOPYS_CANARY_ACTORS` (`__CANARY__`, `__CANARY_ACTORS__`), фаза `app` бере їх зі змінних свого запуску:
   `$env:LITOPYS_CANARY='<4–32 літери/цифри>'; $env:LITOPYS_CANARY_ACTORS='<id>'; scripts/deploy-facade.ps1 -Phase app`
   (апка перезапускається на тому самому образі). Вхід через OAuth (claude.ai) — той самий актор-людина, що й
   власницький токен.
3. У новому чаті клієнта: той самий запит, що в `run.ps1`. Звірити рядки з токеном і записати рядок у матрицю.
4. Вимкнути: `scripts/deploy-facade.ps1 -Phase app` без цих змінних.
